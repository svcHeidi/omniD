# Prior art: LLM agents on scientific simulation software, and how they were evaluated

Method: web search plus abstract/page fetches, 2026-10-10. VERIFIED = stated in the fetched source. JUDGEMENT = mine. Where I only saw an abstract or a search snippet, I say so. Full-text claims (trial counts, per-paper protocols) were NOT checked unless stated.

## 2. General scientific-agent benchmarks (SciCode, ScienceAgentBench https://arxiv.org/abs/2410.05080, PaperBench, MLE-bench, DiscoveryBench)
VERIFIED (via secondary summary): they cover code generation, data-driven discovery, paper reproduction and ML engineering. JUDGEMENT: none targets simulation configuration/execution with a solver-owned validation layer. The simulation-specific ones are CFDLLMBench, FEABench, MooseBench, MD-EvalBench.

## 3. Gap analysis (JUDGEMENT unless cited)
(a) Solver-agnostic layer serving several solvers: I found per-solver MCP servers (Foam-Agent, AutoMOOSE, YADE, COMSOL MCP, chemical-process MCP) and an HPC multi-agent design paper (https://arxiv.org/abs/2603.11515, abstract unreadable). I found no layer whose contract is shared across structurally different solvers (FV vs FE vs GPU FE) with catalogues generated from solver source. Likely novel; treat as "not found", not "absent".
(b) With vs without a layer under controlled isolation: partial precedents are Judge Agent (with/without validation), Foam-Agent and CFDLLMBench (with/without agent framework, but the framework differs in prompts, RAG and model use, not just tools), ChemToolAgent (tools vs none), and mcpbr (https://pypi.org/project/mcpbr/, per-task with/without MCP on SWE-bench). Nothing I found does it for simulation with an oracle, launches and refusals as measures.
(c) Agents doing cross-solver comparison against benchmarks: not found. Closest is Niederer-style cross-solver studies done by humans (not a literature item I searched).
Reviewer pushback to expect: (1) "your layer is a validator, so you are re-deriving the Judge Agent / MooseBench result"; (2) "wrapping a solver in MCP is not novel (Foam-Agent, AutoMOOSE)"; (3) "oracle derived from the same catalogue the layer uses" (circularity); (4) tasks authored by the tool's builder; (5) model has seen the solver docs but not omniD, or the reverse.

## 4. Methodology lessons
- Variance: tau-bench defines pass^k for reliability across repeated trials (https://arxiv.org/abs/2406.12045); an ICC decomposition of between-task and within-task variance is proposed in https://arxiv.org/abs/2512.06710. Report per-task repeated trials with bootstrap CIs, not a single pass rate.
- Cost: https://arxiv.org/abs/2407.01502 argues accuracy-only reporting misleads and benchmarks lack holdouts. Report tokens, dollars, wall time on the same axes, plus a Pareto view.
- Baseline fairness: the cross-paper spread for MetaOpenFOAM (85% self-reported, 55.5%, 6.2% re-run) shows that baselines re-run by a competitor are unreliable; pin versions, prompts and budgets.
- Success must be more than "ran": Foam-Agent and FEABench score executability; MooseBench (39-40% runnable-but-wrong), Judge Agent (42% silent) and JutulGPT show why oracle-judged correctness is needed.
- Contamination: models know OpenFOAM and openCARP tutorials; benchmark tasks drawn from public tutorials leak. Use perturbed/held-out cases (ChatCFD's 110 perturbed variants is a precedent) and say how the agent was prevented from reading the answer, git history or the harness.
- Isolation: separate working dirs, no network to the oracle, same tool budget per arm. mcpbr's per-task container isolation is a model.
- Pre-register tasks, oracle tolerances, models, trial counts and stopping rules before running.

## 5. Judgement: what the paper needs
Must include: (i) oracle-judged correctness (numerical tolerance against a benchmark the agent cannot see), separate from "ran"; (ii) a matched with/without arm where only the layer differs (same model, prompt, tool budget, shell access); ideally a third arm "raw files + good docs" so gains are not just documentation; (iii) at least 5 trials per task per arm with CIs and pass^k; (iv) tokens, cost, wall time, launches and refusals per arm; (v) a failure taxonomy that separates loud, silent-inherited-default (JutulGPT) and wrong-physics errors, and shows which the layer converts into refusals; (vi) held-out/perturbed tasks and at least two model families, with the contamination argument stated; (vii) the cross-solver claim shown by a task an agent completes on 2+ solvers, with the oracle independent of the catalogues; (viii) pre-registration; (ix) honest limits: one domain, tasks authored by the tool's builder.
Novelty claim that I judge defensible: controlled with/without evaluation of a solver-agnostic, source-derived validation layer on simulation tasks, with silent-default failures measured. Not defensible: "first MCP for a solver" or "first validator for generated simulation input".

Three comparator papers to cite (JUDGEMENT):
1. JutulGPT, https://arxiv.org/abs/2603.00214 - same philosophy, no quantitative evaluation; your silent-defaults finding extends it.
2. MooseBench / Intent Fidelity, https://arxiv.org/abs/2605.09360 (with Judge Agent https://arxiv.org/abs/2603.25780 as the with/without-validation precedent) - proves "runs" is not "right".
3. Foam-Agent, https://arxiv.org/abs/2509.18178 - the MCP-exposed solver agent and the standard OpenFOAM baseline, with an execution-only metric you improve on.
(ChemToolAgent https://arxiv.org/abs/2411.07228 is the best methodological precedent for "do tools help" and is worth a fourth citation.)
