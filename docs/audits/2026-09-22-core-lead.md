# Core architecture lead: skeptical pre-Phase-2 audit

Date: 2026-09-22. Role: maintainer. Read `AGENTS.md`, the guidance manifest,
`CLAUDE.md`, maintainer guidance, and the provider integration contract.
This is an assessment and proposed implementation sequence, not approval to
execute the existing Phase 2 snippets literally. Production files and existing
cardiacCore working-tree changes were not edited.

## Recommendation

Keep the three responsibility boundaries: generic orchestration in core,
OpenFOAM syntax and environment mechanics in the OpenFOAM provider, and solver
meaning in each solver adapter. Keep the provider stack and the direction of
one planned write channel. **Revise the Phase 2 contract before implementing it.**
Fix demonstrated composition defects first; otherwise the new write channel
inherits ambiguous ownership and nondeterministic resolution.

The project is closer to this structure than a complete rewrite would suggest.
There is already a capability interface, explicit provider selection, generic
strict planning, structured diagnostics, provenance, leases, durable remediation
transactions, and a proposal/observation repair loop. Their existence does not
prove every public route uses them. The launch-coverage gap is a concrete example.

## Ranked findings

### C1 — P1: provider ordering changes across Python processes

**Observed, reproduced.** `packages/omnidriver/src/omnidriver/core/provider_stack.py:72`,
`order_providers`, constructs dependency sets before `TopologicalSorter`.
TopologicalSorter inserts dependency nodes while iterating these sets. Sorting
the outer provider mapping does not make that insertion order deterministic.

For a provider `org.a` requiring independent providers `org.b` and `org.c`,
`PYTHONHASHSEED=0` produced `[org.c, org.b, org.a]`; seed 5 produced
`[org.b, org.c, org.a]`. The same declared installation can therefore acquire
different sequence order and stack identity. Where sibling providers supply a
`single` hook and the dependent provider supplies no answer, the sibling winner
can change too. Current ordering tests cover independent providers and a single
dependency, but not this case.

**Remedy:** deterministic topological ordering with an explicitly documented
tie-break; reject competing singleton answers from unrelated providers unless
the precedence policy explicitly authorizes them. Sorted order gives
reproducibility, but alphabetical order alone is not evidence of semantic
specificity. Add subprocess tests varying hash seed and input order.

### C2 — P1: write plans cannot faithfully represent the proposed change

**Observed in the proposed code, not a deployed runtime defect.**
`docs/superpowers/plans/2026-09-20-phase2-one-write-channel.md:234`,
`CaseWriteOperation.to_json`, drops `value`. Distinct synthesis contents
serialize identically. The frozen dataclass retains mutable `Any` payloads;
changing a referenced dictionary changes the reviewed operation afterwards.
Both properties were reproduced by executing the exact proposed type block.

There is also no explicit base-content digest, plan schema version, adapter
identity binding, or stale-plan rule. `before` is described as populated by the
writer despite the object being frozen, and mixes execution bookkeeping into
the proposed operation. Those omissions are design gaps, not reproduced
production failures because the new writer does not exist yet.

**Remedy:** a canonical, immutable, JSON-roundtrippable request/plan envelope
with complete intended values or staged-byte content digests, target preconditions,
owner/renderer identities, and a stable plan digest. Journal before-images in
the transaction, separately from the immutable proposal. Refuse stale plans
before modifying the case.

### C3 — P1: Phase 2's writer protocol does not define the patch mechanism

**Observed contract inconsistency.** Task 2 says dispatch both `patch` and
`synthesize` through `CaseWriterCapability`; Task 3 defines only `plan` and
`synthesize`. No patch/render interface is specified. The Task 2 neutral-context
tests expect OpenFOAM-looking text edits without a declared syntax provider.
The plan type commentary says only synthesis needs provider vocabulary, but
patching a nested key also requires file-language semantics.

**Remedy:** core owns preconditions, target containment, leases, journaling,
commit and recovery. The OpenFOAM provider owns parsing/rendering OpenFOAM
dictionary edits. Solver adapters own semantic validation and generation of
requested changes. Define the typed request and renderer contract before the
executor. Distinguish semantic owner from file-format renderer: a solver may
request a change to `system/fvSolution` whose syntax is owned by OpenFOAM.
Do not force one globally exclusive provider to own all formatting and semantics.

### C4 — P1: Phase 2 under-specifies durability and overstates atomicity

**Observed plan gap.** Tasks 1–3 promise transactional, atomic multi-file writes
but specify principally in-process before-images and exception rollback. A
sequence of per-file atomic replacements is not a multi-file atomic transaction.
Crash recovery, concurrent edits, absent-before targets, file modes, rollback
failure, and ownership of recovery are not acceptance tests in the plan.

The existing implementation is a stronger starting point than the plan implies:
`core/runtime/remediation_transaction.py` has durable snapshot/marker handling,
`_atomic_write_bytes`, target manifests, and `_require_transaction_ownership`
requiring case and attempt leases. Reuse must account for materialization
occurring before an execution attempt exists. Passing an arbitrary synthetic
attempt solely to satisfy that API would entangle two different lifecycles.

Task 7 explicitly exempts operation writers from the plan machinery and asks
only for atomic writes, while the global constraints say every write needs a
before-image. Its rendering-failure test does not simulate a failure during
commit and cannot establish crash safety.

**Remedy:** define the scope as agent-managed case mutations, not all bytes
written by a solver. Establish case-level transaction lifecycle and a durable
recovery policy; preserve attempt-specific remediation semantics as a client of
that mechanism. Promise recoverable multi-file commits unless true atomic
visibility is implemented. Test injected failure after each replacement and
restart recovery, including newly-created files and rollback failure.

### C5 — P2: identity reports an implementer rather than the actual answerer

**Observed, reproduced.** `provider_stack.resolutions` credits the most-specific
provider with any callable member. `_first_non_none` actually tries providers
until one returns a non-None answer. In a two-provider probe, `org.b` returned
None and `org.a` supplied the configuration reader; `resolutions['config_value']`
nevertheless credited `org.b`. Union and concatenation capabilities also have
multiple contributors, but identity stores one winner. An absent capability
is assigned the primary provider, rather than explicitly represented as absent.

`ARCHITECTURE.md` already acknowledges that `provides` does not influence
resolution. The implementation goes further: `_implementers` uses all callable
hooks in composition, so a hook described as internal/undeclared still executes.
This is an existing unresolved contract contradiction, not a new discovery.

**Remedy:** decide whether `provides` is an export boundary or merely a
completeness assertion. Name and document that decision accurately. Record
per-member candidate/contributor routes statically; record actual provider
answers dynamically where fallback depends on request/result. Do not call a
static candidate map an execution trace. Bump composition rule version for
changed semantics and deliberately invalidate incompatible prior plans.

### C6 — P2: duplicate provider IDs silently discard one implementation

**Observed, reproduced.** `order_providers` creates `by_id` with a dictionary
comprehension; two objects with the same `plugin_id` yield one provider, with
the later object retained. `driver_context` similarly makes `source_by_id`
before ordering. There is no duplicate-ID guard in this path. Installed entry
point names have ambiguity checks, but distinct names can still share a
provider ID; `_find_installed_provider` returns its first match.

**Remedy:** reject duplicate provider identities independently of entry-point
name and report origins. This is a small supported core correction, not a
justification for replacing the plugin framework.

### C7 — P2: required check coverage is not enforced at dispatch

**Observed source evidence; coordinated with root audit.**
`core/runtime/launch_readiness.py:is_launchable` can reject audit stages marked
`unavailable`, but its own docstring records that dispatch does not supply this
audit and that nothing emits that outcome yet. CLI call sites omit the audit.
The local boolean therefore does not prove required scientific/mechanical
checks ran. Merely passing the existing tuple will not repair absent producers.

**Remedy:** define required checks by workflow/provider, emit explicit
pass/fail/unavailable/not-applicable states, carry them through execution
context, and enforce them at every dispatch edge. Preserve offline planning
as inspectable incomplete evidence. A successful plan must not be described as
a guarantee of convergence or scientific validity.

### C8 — P2: explicit discovery expands only one dependency level

**Observed source limitation, not runtime-probed.**
`core/plugin_discovery.py:_expand_with_requirements` explicitly expands only
the primary provider's requirements. `_default_selection` supports a transitive
closure. A three-tier extension can therefore work through one selection path
and fail through explicit `--plugin`. The shipped environment-plus-solver
stacks do not currently expose this limitation.

**Remedy:** one dependency-closure resolver shared by explicit and default
selection, with cycles, duplicate IDs, ambiguity, and origin tracking tested.

## What to keep, remove, and refactor

- **Keep:** package dependency direction, solver-specific adapters, typed
  capabilities, explicit plugin selection, diagnostics/evidence objects,
  leases and durable remediation, refusal when no adapter can answer.
- **Refactor first:** reproducible stack ordering and identity, complete write
  plan/renderer/transaction contracts, and dispatch evidence plumbing.
- **Retire after migration proves equivalence:** duplicate materialization
  entry points and adapter-side direct case mutations. Keep compatibility
  wrappers for the declared migration interval rather than simultaneously
  deleting every public entry point.
- **Do not add without a demonstrated consumer:** another generic plugin
  dispatcher, a C++ AST framework, or core knowledge of OpenFOAM string syntax.
  Current runtime use of parsed docstring seam metadata is an inspectability
  concern, but this audit did not reproduce a defect justifying its replacement.
- **Split independent work out of Phase 2:** an in-process operation catalog and
  sweeping schema can be useful without blocking transaction correctness.
  Promoting value validation is appropriate only for language-neutral typed
  values. Parsing `'(1 2 3)'` is an OpenFOAM rendering concern; the generic
  concept is a three-component numeric vector. Do not move a solver's textual
  checker into core merely to eliminate duplicate strings.

Autonomy belongs in choosing hypotheses, justified model options, experiment
sequences, and repair proposals. Determinism belongs in resolving the same
declared inputs, validating evidence, changing exactly the reviewed files, and
recording the outcome. The repair loop already binds proposals to observation
digests; apply that discipline to ordinary case writes. Do not turn the agent's
scientific judgment into unexamined default selection.

from omnidriver.core.provider_stack import order_providers, compose, resolutions
